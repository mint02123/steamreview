# 00. 핵심 원칙 (Core Principles)

## 이 문서의 역할

이 문서는 RAG 시스템의 **기준점 문서**이다.
다른 모든 문서(`01_usefulness_score`, `02_evidence_level`, `03_display_decision`, `04_category_signals`, `05_output_schema`)는 여기 정의된 원칙을 따른다.

> Q: 우리 시스템의 핵심 원칙은 무엇인가?
> Q: 점수 예측 결과를 개발자 설명으로 어떻게 변환하는가?
> Q: LLM이 따라야 할 공통 규칙은 무엇인가?

## 1. 시스템 목적

이 RAG 시스템은 **점수 예측 결과(`usefulness_score`)를 개발자용 설명으로 변환**하기 위한 기준을 제공한다.

`usefulness_score`는 Steam 리뷰의 `votes_up` 기반 helpfulness를 예측한 값이다.
이 값은 "리뷰가 유용할 가능성"을 나타내는 우선순위 점수이며,
"개발자가 즉시 조치할 수 있는 리뷰"와 자동으로 일치하지는 않는다.

따라서 이 시스템은 점수와 개발자 관점 사이를 연결하는 해석 규칙을 제공한다.

## 2. 6대 핵심 원칙

다음 6가지 원칙은 모든 판단의 기준이다. 다른 문서의 세부 규칙이 이 원칙과 충돌하면 이 문서가 우선한다.

### 원칙 1. 높은 점수의 리뷰는 핵심 Top-K 후보로 우선 검토한다.
- 핵심 리뷰 후보의 1차 필터는 점수이다.
- 세부 점수 기준은 `01_usefulness_score`를 참조한다.

### 원칙 2. 중간 점수의 리뷰는 카테고리 대표 후보로 사용할 수 있다.
- 전체 Top-K에 들지 못해도 특정 카테고리(bug/balance/qol/feature_request)를 대표할 수 있다면 활용한다.
- 카테고리 신호 판단 기준은 `04_category_signals`를 참조한다.

### 원칙 3. 낮은 점수의 리뷰도 QoL, 기능 추가 등 약한 신호로 활용할 수 있다.
- 점수가 낮다고 자동 폐기하지 않는다.
- 장기 개선 피드백(QoL, feature_request)은 점수가 낮아도 카테고리 요약에 반영할 수 있다.
- 단, 대표 리뷰로는 사용하지 않는다.

### 원칙 4. 근거가 부족한 리뷰는 억지로 대표 리뷰로 만들지 않는다.
- 모든 카테고리를 강제로 채우지 않는다.
- 근거 부족 시 카테고리 상태는 `Not Detected` 또는 `Weak Signal`로 표시한다.
- 근거 수준 판단 기준은 `02_evidence_level`을 참조한다.

### 원칙 5. LLM은 입력에 없는 내용을 추측하지 않는다.
- 패치 정보가 입력되지 않았다면 패치 관련성을 단정하지 않는다.
- 다수 통계가 입력되지 않았다면 "대부분의 사용자가" 같은 표현을 사용하지 않는다.
- 리뷰 원문과 입력 점수에만 근거하여 설명한다.
- 금지 표현·허용 표현 목록은 본 문서 4절·5절을 참조한다.

### 원칙 6. RAG 문서는 점수 예측 결과를 개발자용 설명으로 변환하기 위한 기준을 제공한다.
- 출력은 항상 `05_output_schema`에 정의된 JSON 형식을 따른다.
- 점수는 "선별 기준"이고, 설명은 "최종 해석"이다. 둘은 분리된 단계이다.

## 3. 개발자 유용성의 정의

개발자에게 유용한 리뷰는 단순히 긍정적이거나 부정적인 리뷰가 아니다.
다음 조건 중 **하나 이상**을 만족해야 한다.

1. 특정 문제나 요구가 명확하다.
2. 대상(기능, 시스템, UI, 아이템, 캐릭터, 맵, 서버, 성능 등)이 구체적이다.
3. 사용자가 어떤 상황에서 문제를 겪었는지 일부라도 설명한다.
4. 개발자가 확인하거나 검토할 수 있는 단서를 포함한다.
5. 버그, 밸런스, QoL, 기능 추가 등 개발 피드백 유형으로 해석할 수 있다.
6. 단순 감정 표현을 넘어 개선 방향을 암시한다.
7. 여러 리뷰에서 반복될 경우 우선순위 판단에 활용될 수 있다.

## 4. 금지 표현 (입력에 근거가 없으면 사용 금지)

다음 표현은 입력에 명확한 근거가 없으면 사용하지 않는다.

- "이번 패치로 인해 발생했다"
- "패치 이후 새로 생긴 문제이다"
- "대부분의 사용자가 불만을 가진다"
- "심각한 버그이다"
- "반드시 수정해야 한다"
- "특정 업데이트와 직접 관련된다"
- "유저 이탈의 주요 원인이다"
- "개발자의 의도와 다르다"

이유: 패치노트, 리뷰 작성 시점, 다수 리뷰 통계가 입력되지 않은 상태에서 이런 단정은 환각이다.

## 5. 허용되는 신중한 표현

근거가 부족하거나 불확실한 경우에는 다음 표현을 사용한다.

- "리뷰 내용만 기준으로 보면"
- "~로 해석할 수 있다"
- "~가능성이 있다"
- "~항목으로 검토할 수 있다"
- "추가 확인이 필요하다"
- "구체적인 재현 조건은 부족하다"
- "대표 리뷰보다는 약한 신호로 처리하는 것이 적절하다"

## 6. 판단 흐름 요약

리뷰 1건을 처리할 때 LLM은 다음 순서로 판단한다.

1. **점수 확인** → `01_usefulness_score`로 우선순위 구간 결정
2. **근거 평가** → `02_evidence_level`로 evidence_level 결정
3. **노출 결정** → `03_display_decision`으로 display_decision 결정
4. **카테고리 분류** → `04_category_signals`로 category 결정
5. **출력 작성** → `05_output_schema` 형식으로 JSON 생성

각 단계의 세부 규칙은 해당 문서를 참조한다.
