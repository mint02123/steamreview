# 04. 카테고리 분류 및 상태 판단 기준

## 이 문서가 답하는 질문

> Q: 리뷰를 어떤 카테고리로 분류해야 하는가?
> Q: 한 리뷰가 여러 카테고리에 해당할 때 어떻게 처리하는가?
> Q: 카테고리 상태(Detected/Weak Signal/Not Detected)는 어떻게 결정하는가?

## 핵심 원칙 (요약)

모든 카테고리를 억지로 채우지 않는다([원칙 4](00_core_principles.md)).
카테고리 신호가 있어도 근거가 없으면 대표 리뷰로 만들지 않는다.

## 1. 카테고리 5종

리뷰는 다음 중 하나로 분류한다.

```
bug | balance | qol | feature_request | other
```

| 카테고리 | 정의 | 대표 키워드/표현 |
|---|---|---|
| bug | 의도와 다르게 작동하는 결함 | 크래시, 멈춤, 오류, 안 됨, 튕김, 진행 불가 |
| balance | 게임 내 강함·약함의 형평 문제 | 너무 셈, 너무 약함, 사기 캐릭, 쓰레기 무기, 밸붕 |
| qol | 작동은 하지만 불편한 사용성 | 번거로움, 클릭 많음, UI 답답, 동선 길다 |
| feature_request | 기능·옵션·콘텐츠 추가 요청 및 패치로 추가된 기능/콘텐츠에 대한 구체적 반응 | ~있으면 좋겠다, ~기능 추가, 옵션이 필요, 스토리라인 추가, 월드 생성 개선, 신규 퀘스트, 차량, 기지 건설, 멀티플레이, 새 콘텐츠 |
| other | 위 4종에 해당하지 않음 | 단순 감상, 분류 모호 |

### 1.1 카테고리 경계 케이스 (간단 예)

- "X 무기가 너무 약해서 쓸 이유가 없다" → **balance** (강약 비교)
- "X 무기가 가끔 발사 안 됨" → **bug** (의도와 다름)
- "X 무기 장착 UI가 너무 복잡함" → **qol** (작동하지만 불편)
- "X 무기에 스킨 옵션이 있으면 좋겠다" → **feature_request** (신규 추가)

### 1.2 카테고리 간 경계 통합 표

같은 단어·동일 대상이라도 의미에 따라 카테고리가 갈린다.
각 카테고리별 세부 기준은 [`10_bug_feedback`](10_bug_feedback.md), [`11_balance_feedback`](11_balance_feedback.md), [`12_qol_feedback`](12_qol_feedback.md), [`13_feature_request_feedback`](13_feature_request_feedback.md) 참조.

| 핵심 의미 | bug | balance | qol | feature_request |
|---|---|---|---|---|
| **"broken"** | save/연결/진행 불가 | 너무 강함/형평 붕괴 | — | — |
| **"no option"** | 옵션은 있는데 작동 안 함 | — | — | 옵션 자체가 부재 |
| **무기/캐릭터** | 발사·동작 불가 | 너무 강함/약함 | 장착 UI 동선 | 신규 무기 추가 요청 |
| **UI/메뉴** | 메뉴 클릭 시 크래시 | — | 동선 복잡, 클릭 과다 | 신규 메뉴 추가 요청 |
| **성능** | 갑작스런 비정상 드랍 | — | 일반적 사양 의견 | FPS 옵션 추가 요청 |
| **저장** | 저장 데이터 손상/유실 | — | 저장 슬롯 동선 불편 | 클라우드 세이브 추가 요청 |
| **친구/소셜** | 친구 초대 작동 안 됨 | — | 친구창 동선 불편 | 친구창 직접 초대 추가 요청 |
| **난이도** | — | 구간 내 형평 깨짐 | 진입 단계 동선 | 난이도 옵션 추가 요청 |
| **모드/외부 연동** | 모드 적용 시 크래시 | — | 모드 관리 UI 불편 | 모드 지원 추가 요청 |

### 1.3 한 리뷰에 여러 카테고리 신호가 있을 때

- 작동 불가가 언급되면 **bug** 우선 (다른 신호는 카테고리 카운트로만 사용)
- 작동은 하지만 부재 + 동선 둘 다 언급되면, 핵심이 어느 쪽인지로 판단
  - "있긴 한데 ~ 추가했으면" → **feature_request** 우선
  - "있는데 너무 불편함" → **qol** 우선
- 강약 비교가 핵심이면 **balance**
- 모두 모호하면 **other**

세부 우선순위는 [§2 단일 카테고리 선택 원칙](#2-단일-카테고리-선택-원칙) 참조.

## 2. 단일 카테고리 선택 원칙

여러 유형이 동시에 보일 때 우선순위는 다음과 같다.

## 2. 단일 카테고리 선택 원칙

리뷰 1건은 **가장 중심적인 피드백 유형 1개만** 선택한다.

여러 유형이 동시에 보일 때 우선순위는 다음과 같다.

1. 작동 자체가 안 된다는 언급이 있으면 **bug** 우선
2. 그 외에 강약 비교가 핵심이면 **balance**
3. 작동은 하지만 동선·조작이 핵심이면 **qol**
4. 신규 기능·옵션·콘텐츠의 추가 요청이 핵심이면 **feature_request**
5. 이미 추가된 기능·콘텐츠가 게임 경험을 어떻게 바꾸었는지를 평가하는 리뷰도 **feature_request**로 분류한다.
6. 단, 단순 칭찬만 있고 구체적인 기능·콘텐츠·시스템 대상이 없으면 **other**로 둔다.
7. 어디에도 명확히 속하지 않으면 **other**

### 2.1 복합 의견 예시

**리뷰**: "신규 캐릭터 너무 강하고, 패치 후 가끔 튕기기까지 합니다. 정렬 옵션도 좀 늘려주세요."

**판단**: 작동 불가(튕김)가 가장 심각한 신호이므로 **bug**.
다른 의견(balance, feature_request)은 카테고리 신호로 별도 집계되지만, 이 리뷰의 `category` 값은 1개만 부여한다.

## 3. 카테고리 상태 3단계

전체 카테고리(bug/balance/qol/feature_request)에 대해 **카테고리 상태**를 판단한다.

```
Detected | Weak Signal | Not Detected
```

| 상태 | 의미 |
|---|---|
| Detected | 의미 있는 피드백이 탐지됨 |
| Weak Signal | 약한 신호만 있음 |
| Not Detected | 의미 있는 피드백이 없음 |

### 3.1 Detected — 탐지됨

**조건 (모두 충족)**
- 해당 카테고리 후보 리뷰가 존재한다.
- 후보 중 최고 `usefulness_score`가 충분히 높다(예: 0.60 이상).
- evidence_level이 `sufficient` 또는 `partial`인 리뷰가 1건 이상 있다.
- 대표 리뷰로 보여줄 수 있는 근거가 있다.

**예시**
> Bug: Detected
> 서버 접속 오류와 관련된 구체적인 리뷰가 존재한다.

### 3.2 Weak Signal — 약한 신호

**조건**
- 후보 리뷰는 존재한다.
- 그러나 점수나 근거 수준이 충분히 높지 않다(예: 최고 점수가 0.40~0.60 구간).
- 대표 리뷰로 강하게 제시하기보다 요약에만 반영하는 것이 적절하다.

**예시**
> QoL: Weak Signal
> 사용성 불편 언급은 있으나 구체적인 상황 설명이 부족하다.

### 3.3 Not Detected — 탐지되지 않음

**조건**
- 후보 리뷰가 없다.
- 또는 후보가 있어도 점수와 근거가 매우 낮다(예: 최고 점수가 0.40 미만이고 evidence가 weak/insufficient).
- 억지로 대표 리뷰를 만들지 않는다.

**예시**
> Feature Request: Not Detected
> 기능 추가 요청으로 볼 만한 충분한 근거가 없다.

## 4. 카테고리 상태 결정 절차

전체 리뷰 집합을 처리할 때 각 카테고리에 대해 다음을 수행한다.

1. 해당 카테고리에 분류된 리뷰들을 모은다.
2. 그 중 최고 `usefulness_score`와 최고 `evidence_level`을 확인한다.
3. 다음 표로 상태를 결정한다.

| 후보 리뷰 최고 점수 \ 최고 evidence_level | sufficient | partial | weak | insufficient |
|---|---|---|---|---|
| 0.60 이상 | Detected | Detected | Weak Signal | Not Detected |
| 0.40 ~ 0.60 | Detected | Weak Signal | Weak Signal | Not Detected |
| 0.40 미만 | Weak Signal | Weak Signal | Not Detected | Not Detected |
| 후보 없음 | — | — | — | Not Detected |

### 4.1 빈도에 의한 격상

같은 카테고리에서 동일 취지의 의견이 충분히 많이 반복되는 경우(예: 30건 이상),
- `Weak Signal`을 `Detected`로 한 단계 격상할 수 있다.
- 단 `Not Detected`를 `Detected`로 두 단계 격상하지는 않는다.

빈도 임계값은 운영 데이터에 따라 조정한다.

## 5. 자주 묻는 케이스

### 한 리뷰에 bug와 qol이 둘 다 있을 때 카테고리는?
2.1 절의 우선순위에 따라 결정한다. 작동 불가가 있으면 bug 우선.
다만 카테고리 신호 집계에서는 두 카테고리 모두에 카운트할 수 있다(별도 집계).

### 모든 카테고리가 Not Detected이면?
그대로 Not Detected를 유지한다. 억지로 채우지 않는다([원칙 4](00_core_principles.md)).
출력에는 모든 카테고리에 대해 상태를 명시한다.

### "재밌어요"는 어느 카테고리인가?
**other**. 단순 감상이고 개발 피드백이 아니다.
대부분 evidence_level=insufficient → display_decision=exclude로 처리된다.
